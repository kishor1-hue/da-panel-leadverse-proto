The core move

Leadverse already models work as Tasks → entity type (Order/Lead/Contact) → persona, each persona a workflow with a slug shaped {bu}-{entity}-{action}-by-{actor} (confirmed live: b2c-order-cancellation-by-rm). Its current Order personas — Cancellation, Delivery Schedule, Delivery, FinOps, Qc, Registration, RM, VAS Refurb — cover every post-booking stage except the test drive itself.

Reuse as-is

Assign DA

Leadverse's ManualAssignmentModal + assign-direct endpoint already does "pick a candidate, ranked, from a modal." Add a per-DA daily-capacity check and point it at DA candidates.

Extend

DA shift status

The header's online/offline AssignmentStatusToggle is one flag away from DAP's five-state CHECK_IN/AVAILABLE/ON_BREAK/DA_RM_WORK/CHECK_OUT.

Reuse as-is

Oversight tables

Cx Hub View, DA List, Car Level View are new personas/columns on the existing Tasks table — no new component.

Net new

Walk-in intake + car selection

Customer capture, car listing/compare, and order creation for a walk-in with no pre-existing booking — a genuinely new stepper flow, distinct from checking in a customer who already booked online.

Net new

VAS + payment collection

DA presents VAS, confirms selection, then generates a QR/bank-transfer payment request in-app — a new in-person collection flow, not just a read-only token-paid reflection.

Extend

Left-pane contract

The header/tabs/sections JSON contract already covers avatar, status badge, call/WhatsApp/SMS actions — needs Booking/Test-Drive tabs added to its vocabulary.

Two receptionist flows, one screen

An existing/pre-booked customer only needs Check-in → Assign DA. A walk-in with no booking needs the full intake first: Customer Details → Select Car (with compare) → Order Created → Check-in → Assign DA. Both live on the same Test Drive Detail screen — the stepper configuration is chosen dynamically by whether the order already exists.

Still open

Leadverse has no role system today comparable to DAP's eight roles — gating is "authenticated + tenant chosen" plus a few hardcoded persona checks. DAP backend's own user-role-mapping.yml is the closest working model to port. Whether Hub/Virtual/Home stay three distinct workflow families or get unified is still an open product decision.
